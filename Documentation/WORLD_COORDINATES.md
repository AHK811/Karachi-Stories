# World coordinate foundation (M2.0)

Machine-readable source of truth: [`config/world_coordinates.json`](../config/world_coordinates.json),
regenerated by [Tools/osm_importer/derive_world_origin_m20.py](../Tools/osm_importer/derive_world_origin_m20.py)
and asserted by [Tools/osm_importer/test_world_coordinates_m20.py](../Tools/osm_importer/test_world_coordinates_m20.py)
(16 checks). Evidence copy: `GIS/validation/world_coordinates_m20.json`.

Status: **proposed freeze, awaiting project-owner approval.** Nothing here is derived from a guess about
the boundary — every figure comes from the frozen canonical GIS dataset v1.0.0, which this milestone did
not modify (asserted by test 13, 8/8 checksums).

## The five locked numbers

| Name | Value | Meaning |
|---|---|---|
| `E0` | **225280 m** | Easting of world origin, chunk-tile-aligned (`225280 = 440 × 512`) |
| `N0` | **2841088 m** | Northing of world origin, chunk-tile-aligned (`2841088 = 5549 × 512`) |
| `vertical_origin_m` | **0.0 m** | Documented fallback, **not** a surveyed height — see "Elevation" below |
| chunk size | **512 m** | 256 m is a required benchmark, not a rejected alternative |
| working CRS | **EPSG:32642** | WGS 84 / UTM zone 42N; storage CRS stays EPSG:4326 |

`E0`/`N0` are **deterministic**, not chosen by taste:

```
E0 = floor(min_easting  / 512) * 512   over the L1 Karachi Division extent
N0 = ceil (max_northing / 512) * 512   over the L1 Karachi Division extent
```

with the measured division extent `E 225502.25 … 356734.09`, `N 2703445.33 … 2840930.24`. Rounding
outward to the 512 m grid makes **every chunk index inside the division non-negative**, so a chunk can
never be named `-1,3`. Test 02 recomputes both from the frozen layer and fails if they drift.

The origin uses **L1 (administrative) only**. L2 land and L3 water extend to `E 215798 … 369673`
because that is how they were cut from the gridded coastline products — a processing artifact of the
clip box, not a world boundary. Sizing the world from the masks would silently widen it by
**22.64 km east-west and 30.98 km north-south** of empty sea and desert beyond the administrative
division (mask span 153.87 × 168.47 km versus division span 131.23 × 137.48 km). Test 16 asserts the flag and the rule.

## Axes

Godot 4 is right-handed, Y-up. The mapping is:

```
game_x =  easting_m  - E0        # east  -> +X
game_z =  N0 - northing_m        # north -> -Z   (south is +Z)
game_y =  elevation_m - vertical_origin_m
```

So **north is negative Z**. This is the single most common way to silently mirror an entire city, so
it is asserted, not explained: test 06 takes Saddar (67.0200, 24.8600) and northern Malir
(67.1600, 25.0200) and requires `game_x` to increase (74,667.0 → 89,055.6) while `game_z` decreases
(90,188.5 → 72,664.5), i.e. the more-northern point is at more negative Z.

## Chunk conventions

```
chunk_x  = floor((easting  - E0) / 512)
chunk_z  = floor((N0 - northing) / 512)
local_x  = easting  - (E0 + chunk_x * 512)      # in [0, 512)
local_z  = (N0 - northing) - chunk_z * 512      # in [0, 512)
```

The division covers **257 × 269 = 69,133 chunks** (153.9 × 168.5 km) at 512 m. That count is an
address space, not a workload — nothing is generated for it in M2.0 and the runtime streams a small
neighbourhood.

Test 09 confirms chunk-local coordinates lie inside `[0, 512)` and test 08 pushes **all 2,074 L1
vertices** (every exterior *and* interior ring of the division plus the 7 districts) through the chunk index and requires
zero out-of-range hits. A feature exactly on a tile edge takes the tile to the south/east by the
`floor` definition; edge-case clipping rules are an M4 task, but the index rule is already fixed here.

### Distortion revision

[`CRS_AND_MEASUREMENT.md`](CRS_AND_MEASUREMENT.md) and the frozen v1.0.0 manifest record **+211 ppm**
(k = 0.99994 … 1.000211). That figure came from **7 sample points in the built-up core**, which is the
eastern, lower-distortion part of the division. The M2.0 measurement samples the **whole administrative
extent**, including the far western Keamari/Hub boundary and the northern Malir extent, where
transverse Mercator distortion is larger because the distance from the 69°E central meridian grows.
**496.7 ppm (about 50 cm per kilometre) is the correct city-wide worst case and supersedes 211 ppm for
any statement about the full playable world.** The old number is not deleted from history; it is
mislabeled as a core-sample figure, and [DECISIONS.md](DECISIONS.md) D-043 records the change.

This does not reopen the CRS decision. 50 cm/km is far below anything gameplay can detect, area
agreement between geodesic and planar methods stays at 0.0511%, and a custom central meridian at
67.05°E was evaluated: it lowers distortion but breaks the locked EPSG:32642 decision and every
UTM-native tool around OSM, so EPSG:32642 is retained (`alternatives_evaluated` in the config).

### Why chunk-local coordinates are mandatory, by measurement

Godot `Vector3` is float32. The largest global game coordinate for the whole division is 137,643 m,
and at that magnitude the gap between adjacent representable float32 values is **15.62 mm** — larger
than a door hinge tolerance and visible as vertex jitter on a 1:1 city. Inside a 512 m chunk the same
gap is **0.061 mm**, 256× better. Therefore: keep **64-bit global projected coordinates** as the
canonical position of every feature, and only convert to `Vector3` after subtracting the chunk
origin. Test 10 fails if either side of that comparison stops being true.

## Elevation

`vertical_origin_m = 0.0` is a **documented fallback, not a datum**. No licensed DEM exists in this
repository, so `vertical_datum` is recorded verbatim as
`UNSET - no licensed elevation source; game Y uses a documented ground-height fallback of 0 m`.
Test 14 requires the string to contain `UNSET` and the value to stay 0.0, so nobody can quietly
present a flat plain as surveyed terrain. Introducing elevation is a licensed-data decision (M5+),
and when it arrives it needs a named vertical datum and a migration entry here.

## Godot side: specification, not verified code

The engine is **not installed on this machine**. `godot` is absent from `PATH` and from C:, D: and E:
to depth 3; `project.godot` declares `features 4.7 + GL Compatibility`, but a string in a project file
is not evidence of a runnable engine. Rather than assume a version, the config records
`godot_executable_found: false` and test 15 asserts that honesty.

Consequences the beginner should understand: the transform formulas above are implemented and tested
**in Python only**. No GDScript equivalent exists yet — M2.0 was authorized as the coordinate
foundation, and the existing starter scripts `scripts/player.gd` and `scripts/world.gd` were left
untouched. This document is the specification M6 implements against, on a pinned engine, with a headless
test that compares Godot's own numbers to the table above. No claim of "the game loads this correctly"
exists in this milestone, because nothing was run in a game engine.

## Floating origin

Deferred to M2.5. The rule is fixed now, in advance: global projected coordinates stay 64-bit and are
kept separate from local `Vector3`; a rebase must move physics bodies, navigation, cameras, particles,
audio and active chunks **together or not at all**. Nothing in M2.0 rebases anything.

## Re-verifying this yourself

From WSL, inside the repository root:

```bash
cd Tools/osm_importer
python3 derive_world_origin_m20.py          # rewrites config + evidence from the frozen layers
python3 test_world_coordinates_m20.py; echo "exit=$?"
```

Expected: 16 `PASS` lines, `TOTAL 16  PASS 16  FAIL 0`, `exit=0`, and `git diff` on
`GIS/canonical/` stays empty. Re-running `derive` must produce a byte-identical config; if `E0`/`N0`
change, that means the boundary layer changed and this document needs a version bump, not a quiet edit.

## What M2.0 explicitly does not do

No PBF download, no road/building/terrain geometry, no chunk files, no GLB, no Godot scene changes,
no modification to canonical v1.0.0. Those belong to M2.1+ and require their own approval.
